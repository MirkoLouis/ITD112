A hands-on lab applying Module 2's integration workflow — building requests for two differently-shaped APIs, sending them with timeouts, retries and a disk cache, parsing nested JSON with per-property unit conversion, joining static soil onto daily weather, and answering six analytical questions with charts — as one Streamlit app across several Mindanao sites.
What you'll be able to do after this module

Watch for
The SoilGrids REST API is a beta service with no uptime guarantee, and ISRIC has paused it before. The two data sources, and the sites

Everything in this app comes from two public APIs. Neither needs a key. They have almost nothing in common except the coordinate you hand them — which is precisely what makes the join in §8 worth doing.

SoilGrids has no values over water, and returns null for a coordinate that falls on a lake, a river, or the sea. That is not an error — the request succeeded, the map simply has no estimate there. Step 3 — Build the request

A request is an endpoint URL plus query parameters. The two APIs want those parameters in genuinely different shapes, and getting that difference right is most of this step.
Open-Meteo: one call, every site

It accepts comma-separated coordinate lists, so five sites travel in a single GET. The response comes back as a JSON array, one object per site, in the order you sent them.
SoilGrids: one call per site

It takes a single point. Five sites means five GETs, in a loop, with a pause between them — and the property key is repeated once per soil property rather than comma-joined.

def build_weather_request(sites, start, end):
    """Open-Meteo accepts comma-separated coordinates, so one request covers every site."""
    params = {
        "latitude":  ",".join(str(v) for v in sites["lat"]),
        "longitude": ",".join(str(v) for v in sites["lon"]),
        "start_date": start,
        "end_date": end,
        "daily": ",".join(DAILY_VARS),
        "timezone": TIMEZONE,
    }
    return {"api": "Open-Meteo", "label": "All sites", "url": WEATHER_URL,
            "params": params, "full_url": full_url(WEATHER_URL, params)}

def build_soil_request(site, lat, lon):
    """SoilGrids takes one point per request. 'property' repeats once per soil property."""
    params = [("lat", lat), ("lon", lon), ("depth", SOIL_DEPTH), ("value", "mean")]
    params += [("property", p) for p in SOIL_PROPERTIES]      # repeated keys
    return {"api": "SoilGrids", "label": site, "url": SOIL_URL,
            "params": params, "full_url": full_url(SOIL_URL, params)}

Note the params type: a list of tuples, not a dict. A dict cannot hold the key "property" five times — the last one would overwrite the rest and you would get one soil property back instead of five.

def full_url(url, params):
    """The exact URL that will be sent, with the query string encoded."""
    return requests.Request("GET", url, params=params).prepare().url

Worth building a page around: printing the prepared URL shows students the exact string that goes over the wire, percent-encoding included, without having to trust that requests did the right thing.
Why not build the URL by hand?
Because requests already encodes every key and value correctly — the commas in your coordinate list, the spaces in "Davao (Calinan)", the lot. Hand-concatenated query strings are where percent-encoding bugs live, and they fail silently: the server returns something, just not the thing you meant to ask for.

Step 4 — Send the request, defensively

This is the section that separates a demo from an application. Four protections, each one answering a specific failure you will otherwise meet in front of the class.
Timeout
timeout=60 on every call. Without it a stalled connection hangs the app forever, with no error to debug.
Retry with backoff
total=3, backoff_factor=2 on 429 and 5xx — waits 2s, 4s, 8s. A 400 is deliberately not retried.
Disk cache
Every successful response is written to cache/ under a hash of its URL and parameters. A repeat request never reaches the network.
Fair-use pause
About 12 seconds between SoilGrids calls — roughly five per minute, inside what a free beta service can absorb.

from requests.adapters import HTTPAdapter
from urllib3.util.retry import Retry

@st.cache_resource
def http_session():
    """Session that retries on rate limiting (429) and server errors (5xx)."""
    retry = Retry(total=3, backoff_factor=2,
                  status_forcelist=(429, 500, 502, 503, 504),
                  allowed_methods=("GET",))
    s = requests.Session()
    s.mount("https://", HTTPAdapter(max_retries=retry))
    s.headers["User-Agent"] = "itd112-lab1/1.0"
    return s

st.cache_resource builds the session once and reuses it across re-runs, so connections are pooled instead of re-opened on every interaction. Setting a User-Agent that identifies your app is basic courtesy toward a free public service.

def send(req):
    """GET the request and return the response record. A response saved on disk is
    reused instead of calling the API again."""
    key = hashlib.sha1(
        (req["url"] + json.dumps(req["params"], sort_keys=True, default=str)).encode()
    ).hexdigest()
    path = CACHE_DIR / f"{key}.json"

    if path.exists():                                   # cache hit — no network at all
        text = path.read_text(encoding="utf-8")
        return {"status": None, "from_cache": True, "data": json.loads(text)}

    r = http_session().get(req["url"], params=req["params"], timeout=60)
    r.raise_for_status()                                # 4xx / 5xx -> exception
    data = r.json()
    CACHE_DIR.mkdir(exist_ok=True)
    path.write_text(json.dumps(data), encoding="utf-8")
    return {"status": r.status_code, "from_cache": False, "data": data}

The cache key hashes the URL together with the sorted parameters, so changing a single coordinate or one date produces a different file — and asking the identical question twice never costs a second request.

for i, req in enumerate(soil_reqs):
    try:
        res = send(req)
    except requests.RequestException as exc:
        raise RuntimeError(
            f"SoilGrids failed for {req['label']}: {exc}. The SoilGrids REST API is a "
            "beta service and is sometimes paused. Try again later.") from exc
    soil_res.append(res)
    if not res["from_cache"] and i < len(soil_reqs) - 1:
        time.sleep(SOILGRIDS_PAUSE_S)                   # fair use, ~5 calls/minute

Two details worth copying: the pause is skipped entirely on a cache hit, so a second run is instant; and the raw exception is re-raised with a sentence that tells the reader what to do about it, rather than a bare stack trace.
What the response log should show you
Render the status code, round-trip time, and payload size for every call in a small table. On a first run every row reads 200 with a few hundred milliseconds against it; on a second run every row reads "saved copy" with no time at all. That contrast is the lesson about caching — make it visible rather than asserting it in a comment.

Step 5 — Parse the JSON into tables

JSON is nested; analysis needs rectangles. The two responses need genuinely different treatment, because they are nested in different ways and for different reasons.
Open-Meteo: parallel arrays become columns

def parse_weather(data, sites):
    """Each site's 'daily' block holds parallel arrays; each array becomes a column."""
    results = data if isinstance(data, list) else [data]   # one site returns an object
    frames = []
    for site, res in zip(sites["site"], results):
        df = pd.DataFrame(res["daily"])
        df.insert(0, "site", site)
        frames.append(df)
    return pd.concat(frames, ignore_index=True)

The isinstance check is not defensive padding — Open-Meteo genuinely returns a bare object for one coordinate and an array of objects for several, so a one-site run crashes without it. The site name has to be inserted by hand, because the response identifies sites only by their position in the array.
SoilGrids: walk the nesting, then divide

def parse_soil(data, site):
    """One row per soil property. SoilGrids stores integers; dividing by d_factor gives
    conventional units (g/kg -> %, pH x10 -> pH, dg/kg -> g/kg)."""
    rows = []
    for layer in data["properties"]["layers"]:
        raw = layer["depths"][0]["values"]["mean"]
        unit = layer["unit_measure"]
        rows.append({
            "site": site,
            "property": layer["name"],
            "raw_mean": raw,
            "mapped_units": unit.get("mapped_units"),
            "d_factor": unit["d_factor"],
            "value": np.nan if raw is None else raw / unit["d_factor"],
            "target_units": unit.get("target_units"),
        })
    return pd.DataFrame(rows)

Keeping raw_mean, d_factor, and value as three separate columns turns the conversion into something the reader can audit on screen — 352, ÷10, 35.2 — instead of a number they have to take on faith. Show this table in the app.
value  =  raw_mean  ÷  d_factorread the divisor from the response, never hardcode 10
clay 352 ÷ 10 = 35.2 %phh2o 58 ÷ 10 = pH 5.8

def soil_table(soil_long, sites):
    """Pivot to one row per site, one column per property, and attach coordinates."""
    wide = (soil_long.pivot(index="site", columns="property", values="value")
            .reindex(columns=SOIL_PROPERTIES).reset_index())
    wide.columns.name = None
    return sites.merge(wide, on="site", how="left")

Long-to-wide: the audit table above has one row per property, but the join in §8 needs one row per site. The reindex fixes the column order to SOIL_PROPERTIES rather than whatever order the pivot produced.
Handle the nulls out loud
A coordinate over water returns null for every property, which becomes NaN here. Do not drop those rows silently and do not fill them with zero — a zero would draw a real bar on Q4's texture chart. Detect them and say so:

missing = soil.loc[soil["clay"].isna(), "site"].tolist()
if missing:
    st.warning(f"SoilGrids returned null for: {', '.join(missing)}. The map has no "
               "value at that exact point (water, a built-up area, or a gap in the "
               "map). The request still succeeded; try moving the point slightly.")

Step 6 — Integrate the two sources

Now the shapes have to be reconciled: many weather rows per site, exactly one soil row per site. A left join copies each site's soil values onto every one of its daily rows — the broadcast from Module 2 §11, done by pandas across several sites at once.

def integrate(weather, soil):
    daily = weather.merge(soil, on="site", how="left")          # the join
    daily["time"] = pd.to_datetime(daily["time"])
    daily["month"] = daily["time"].dt.month
    daily["water_balance_mm"] = (daily["precipitation_sum"]
                                 - daily["et0_fao_evapotranspiration"])

    summary = (daily.groupby("site", sort=False)
               .agg(rain_mm=("precipitation_sum", "sum"),
                    et0_mm=("et0_fao_evapotranspiration", "sum"),
                    water_balance_mm=("water_balance_mm", "sum"),
                    temp_mean_c=("temperature_2m_mean", "mean"))
               .reset_index().merge(soil, on="site"))
    return daily, summary

Two tables come out, not one. daily is the full joined record — every site, every day — and drives Q1, Q2, and Q3. summary is one row per site, weather totals beside soil properties, and drives Q4, Q5, and Q6.
Table	Shape	Built by	Feeds
weather	one row per site per day	parse_weather()	the join
soil	one row per site	soil_table()	the join
daily joined	sites × days, soil broadcast across	integrate()	Q1, Q2, Q3
summary joined	one row per site	integrate()	Q4, Q5, Q6

Three sites over one year is roughly 1,095 daily rows and 3 summary rows — worth showing as metrics on the page, because the count is what makes the broadcast concrete.
Check the join before you trust it
A left join that matches nothing still succeeds — it just fills every soil column with NaN. Confirm the row count is unchanged from the weather table and that clay is populated, before plotting anything. A site name that differs by a stray space between the two tables is the usual culprit, and the charts downstream will simply look empty rather than complain.

Step 7 — Analyse: six questions, six charts

Module 2 §12 gave the rule — start from the question, then choose the encoding. Here are the six questions this dataset answers, and the chart each one earns. Two of them (Q5 and Q6) cannot be answered by either API alone; those are the ones that justify the whole integration.
	Question	Chart	Built from
Q1	How does temperature change over time?	Line chart, 7-day rolling mean	daily · Open-Meteo
Q2	Does rainfall meet evaporative demand?	Combo: monthly bars + ET0 line, one mm axis	daily · Open-Meteo
Q3	How variable is daily rainfall?	Box plot by month	daily · Open-Meteo
Q4	What is the topsoil texture at each site?	100% stacked bar	summary · SoilGrids

Q2 — the honest combo chart

def chart_q2(daily, site):
    """Monthly rainfall bars vs reference ET0 line, on the same mm axis."""
    m = (daily[daily["site"] == site].groupby("month")
         [["precipitation_sum", "et0_fao_evapotranspiration"]].sum()
         .reindex(range(1, 13), fill_value=0))
    deficit = m["precipitation_sum"] < m["et0_fao_evapotranspiration"]

    fig = go.Figure()
    fig.add_bar(x=MONTHS, y=m["precipitation_sum"], name="Rainfall (surplus month)",
                marker_color=np.where(deficit, COLORS["sky_pale"], COLORS["sky"]))
    fig.add_scatter(x=MONTHS, y=m["et0_fao_evapotranspiration"], name="Reference ET0",
                    mode="lines+markers", line=dict(color=COLORS["sun"], width=2.5))
    fig.update_yaxes(title="mm per month", rangemode="tozero")
    return fig

One y-axis, both series in mm, rangemode="tozero" so the bars are not truncated. Deficit months are shaded paler — colour reinforcing the comparison the chart already makes geometrically, rather than carrying it alone.
Q4 — normalise before you stack

tex = summary.set_index("site")[["sand", "silt", "clay"]].dropna()
tex = tex.div(tex.sum(axis=1), axis=0).mul(100).sort_values("clay")

SoilGrids texture fractions rarely sum to exactly 100 — they are independent model outputs, not shares of a whole. Normalising each row to 100% is what makes a stacked bar legitimate; skipping it gives bars of visibly different lengths that invite a comparison the data does not support.
Q5 — the chart that needs both APIs

s = summary.dropna(subset=["clay", "soc"])
fig.add_scatter(
    x=s["clay"], y=s["water_balance_mm"], mode="markers+text", text=s["site"],
    marker=dict(size=14 + 26 * s["soc"] / s["soc"].max()),   # bubble size = SOC
)
if len(s) >= 5:                                  # least-squares trend line
    slope, intercept = np.polyfit(s["clay"], s["water_balance_mm"], 1)
    r = np.corrcoef(s["clay"], s["water_balance_mm"])[0, 1]
    fig.add_scatter(x=xs, y=slope * xs + intercept, mode="lines",
                    name=f"Linear fit (r = {r:.2f}, n = {len(s)})")
fig.add_hline(y=0, annotation_text="rainfall = ET0")

Clay comes from SoilGrids, the water balance from Open-Meteo, and organic carbon sizes the bubble — three variables, two APIs, one chart. The horizontal line at zero is the interpretive anchor: above it a site gained water over the period, below it demand exceeded supply.
Say what five points can and cannot support
The trend line only appears at n ≥ 5, and the legend prints both r and n so nobody reads it as an established relationship. Five sites is an exploratory sketch, not evidence. Your write-up should say so in as many words — naming the limitation is part of the grade, not a hedge against it.

What provenance means in practice
Provider, access date, licence, and the caveat. For this lab that last part is specific: SoilGrids is a beta service that may be paused, and the values are modelled estimates with quantified uncertainty, not measurements taken at your coordinate. A dashboard that presents them as ground truth is misleading even though every number in it is correct.
